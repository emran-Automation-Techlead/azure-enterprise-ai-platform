# Responsible AI

> **This project demonstrates engineering patterns for responsible AI. It is not a certified legal, regulatory, compliance, medical, financial, employment, or safety assessment.**

## 1. Purpose
Show how Responsible AI controls can be built *into* the architecture of a RAG application, instead of added as documentation afterwards.

## 2. AI system description
An enterprise IT assistant. A question is routed, retrieved against synthetic enterprise documents in Azure AI Search, answered by Azure OpenAI only from those documents, and then reviewed by a Responsible AI layer that adds sources, a risk level and a human-review decision.

## 3. Intended use
IT support engineers and employees asking troubleshooting or policy questions, as a first pointer to existing documentation.

## 4. Out-of-scope use
Autonomous production changes; decisions about people (employment, credit, health, legal); safety-critical decisions; anything to bypass security controls; any use with real confidential data without a proper assessment.

## 5. Fairness
For this assistant, fairness means consistent treatment of equivalent requests, no profiling of users, and no decisions based on protected characteristics. The system takes no user identity or demographic input at all.
*Fairness considerations are incorporated through consistent rules, evaluation scenarios, and human oversight.* This is **not** a mathematical fairness guarantee, and the evaluation set contains no demographic fairness tests.

## 6. Transparency
Every response shows: "This response was generated by AI…" (the wording changes when no enterprise sources were used), the query type, sources, grounding status, risk level and human-review status. The risk label always reads "Portfolio demonstration risk classification".

## 7. Explainability
No chain-of-thought is exposed. Instead the user sees which documents were used (ID, title, category, relevance), a one-line explanation ("Response based on 1 retrieved enterprise document(s)" or why nothing was used), and the reasons human review was requested.

## 8. Privacy
- Credential-like text in a question is redacted before it reaches the model or the logs.
- The user gets "Please avoid sharing passwords, authentication tokens, or other sensitive credentials."
- Telemetry holds counts, latency, query type, risk and flags only: never the question or answer text.
- Known limit: redacting a secret can leave a question too vague to answer.

## 9. Safety
Layered, because each layer has gaps:
| Layer | Catches | Does not catch |
|---|---|---|
| Router rules | prompt injection, credential requests, security bypass, disabling security controls, production changes, secrets in input | rephrasings not matched by the patterns |
| Azure AI Content Safety | hate / violence / sexual / self-harm at severity >= 4 | calmly worded harmful intent; prompt injection (observed in testing) |
| Local rules | requests to build malware/weapons or steal data | anything outside a small deny-list |
| Output scan | leaked instruction text; credential-like values | subtle leaks |

## 10. Reliability
The assistant must not invent enterprise information. If the best retrieved match is weak (below 0.65), the model is **not called** and the fixed message is returned: *"I don't have enough information in the enterprise knowledge base to answer this confidently"*, with next steps. Citations to documents that were not retrieved are detected and flagged.

## 11. Accountability
Every response carries metadata (query type, grounded, risk level, flags, sources, human-review reasons) so a decision can be traced.

## 12. Human oversight
`human_review_required` is set for: risk MEDIUM or above, conflicting sources, insufficient evidence for an enterprise question, sensitive input, an unsupported citation, or a security-sensitive request. The assistant never presents itself as the final authority.

## 13. Grounding
Enterprise questions are answered only from retrieved documents. General-technology questions are answered separately and labelled *not* from the enterprise knowledge base.

## 14. Prompt injection
Instruction-override attempts are blocked by rules **before** any search or model call, so there is nothing to talk the model out of. Documents are also treated as data, not instructions, in the grounded prompt.

## 15. Risk classification
LOW / MEDIUM / HIGH / CRITICAL, assigned by deterministic rules (e.g. "disable security controls" = HIGH, "bypass security controls" = CRITICAL). **Portfolio demonstration risk classification: not a certified framework.**

## 16. Evaluation methodology
`evaluation/evaluate.py` runs 10 hand-written cases, 3 runs each, across 8 dimensions: classification, grounding, refusal, safety, prompt injection, transparency, human oversight, consistency. See `docs/screenshots/16-responsible-ai-evaluation.png`.

Result of the recorded run: classification 10/10, grounding 10/10, refusal 3/3, safety 3/3, prompt injection 1/1, transparency 10/10, consistency 10/10, **human oversight 9/10**. The failure (TC09) is documented, not hidden: for "What is the VPN troubleshooting procedure?" the model sometimes cites both VPN documents and surfaces their genuine timeout conflict, which triggers review.

## 17. Known limitations
- A 10-case evaluation does **not** prove production-level safety.
- The grounding threshold (0.65) was set from a small calibration; one high-risk case scored 0.66.
- The conflict flag is an LLM judgement and is not fully consistent.
- Content Safety missed a calmly worded harmful request and does not detect prompt injection.
- Synthetic data only; no demographic fairness testing.

## 18. Future improvements
Azure AI Content Safety Prompt Shields; semantic ranker; claim-level conflict detection against the answer text; an expanded, versioned evaluation set run in CI; red-team testing; per-user document access control; audit log export.
